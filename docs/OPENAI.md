# OpenAI setup

Catchy supports `rules` (default), `ollama` and `openai`. n8n is not needed for detection: FastAPI calls the model directly. The optional alert webhook is separate; no workflow or external messaging service is activated by this integration.

## Windows

1. Sign in to [OpenAI API keys](https://platform.openai.com/api-keys) and create a project key. Ensure your project has API billing/credits and access to the selected model. An API key cannot be generated by Catchy.
2. Extract the project and double-click `START-OPENAI.bat`. The first run installs Python dependencies, just like the standard launcher.
3. Paste the key into the hidden terminal prompt. Nothing appears while typing; press Enter. Do not paste keys into chat or frontend files.
4. Keep the terminal open and use Type or paste with a synthetic example. A fallback notice means the model request did not succeed; rules still run.

The prompt sets the key only in the server process environment. Closing the launcher ends that process; it does not write a key file. Reopening asks again unless you already supplied OPENAI_API_KEY in the environment. `START-WINDOWS.bat` retains the normal environment-based configuration.

## Server configuration

Set `LLM_PROVIDER=openai`, `OPENAI_API_KEY` to your secret, and optionally `OPENAI_MODEL` (default `gpt-4o-mini`). This default supports structured output; availability depends on your project. `LLM_TIMEOUT` accepts 0.1–10 seconds, default 5 for OpenAI and 1.2 for Ollama. It is an HTTP phase timeout, not an end-to-end latency guarantee. Requests are not automatically retried.

Python launchers read the environment; copying `.env.example` alone does not configure Python. Docker Compose reads `.env` and forwards the OpenAI fields to the application container. Production should inject the key through deployment secrets. Never put a real key in `.env.example`; real `.env` files are excluded from Git and the source ZIP. Do not publish resolved Compose configuration because it contains environment secrets.

`GET /api/health` includes `llm.provider` and `llm.configured`. Configured means a key is present, not that billing, authentication or connectivity has been tested. A successful analysis returns `model_status=connected`; a failed model request returns `model_status=unavailable` alongside the rules result. Health never calls OpenAI or exposes the key. Unit tests mock all OpenAI traffic and require no credentials.

## Processing and limitations

Only up to eight recent text turns, each capped at 1,500 characters, are sent after best-effort redaction. Older turns remain covered by rules. Raw audio is not sent to OpenAI by this adapter. Requests use the Responses API, strict JSON schema, `store=false`, a 1,600 output-token cap, no tools and no redirects. Exact evidence quotes, turn numbers and action-request gates are validated locally; a model cannot remove rule findings.

Redaction may miss personal information. `store=false` is not a promise of zero provider retention; review [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data). Repeated turns are separate API requests and can incur charges. Set project limits in your OpenAI dashboard and monitor usage. Guest requests also use the configured model, subject to existing application rate limits; do not expose a paid deployment without monitoring.

Missing/invalid keys, unavailable models, quota limits, timeouts, refusals and malformed output all fall back to rules without exposing provider error bodies. Check your project key, billing, model access and outbound HTTPS access if fallback persists. Rules-only evaluation scores do not measure OpenAI accuracy or cloud latency. Real provider validation remains required after supplying a valid key.

Sources: [API quickstart](https://developers.openai.com/api/docs/quickstart), [structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs).
